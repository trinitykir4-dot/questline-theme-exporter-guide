WEB GUIDE

Figma Theme Exporter

This plugin is used to ship themable pop-ups from Figma to the web. It's powerful, but can be complex in practice. This guide brings together practical patterns and approaches to make the workflow clearer and easier to navigate.

This web version is built on top of the original Figma guide by Michal Mosat, with additional practical context from hands-on use of the workflow.

Pick how you want to approach the workflow

Both approaches ship the same final ZIP. Approach A is the everyday route — fast and safe. Approach B is for designers building a brand-new theme structure from scratch, or rebuilding a broken file.

Mockup — final assembly

Stands apart from the seven components. Holds instances of all of them.

Components vs Mockup. All seven components — background, header, rewards, quests, button, timer, wheel — live as Main Components inside the components frame. The Mockup (e.g. Questline: ML SuperBowl) stands apart from those seven — it's the assembled view full of Child Components (instances of the mains). The mockup is itself a Component too, so you can drag instances of it into Mobile / Desktop preview frames for visual QA. Any change to a Main Component reflects immediately in every instance — that's the whole reason for working in components.

Final Design rules (the assembled mockup):

  • Layout — header on top, rewards just below. Timer is flexible: place it in the upper part right under rewards, OR in the lower part just above the button — depends on the design and the space available. Button is always at the bottom.
  • Structure must be clean — every component sits as its own separate top-level layer in the mockup frame (header / rewards / timer / button / quest1 / quest2 / … / background). No nesting, no groups around them.
  • Items (quests) are named exactly quest1, quest2, quest3, … in the layer panel — these names are what the plugin reads.
  • Never edit anything in the mockup directly — no resize, no recolour, no text edit. All changes go into the source Component in the components frame and propagate down. (See Mistakes for what breaks if you don't.)

Correction on the in-Figma guide: the Description shown there is not a separate component — it lives inside the background component. Don't try to ship it as its own layer/component, it'll fail validation.

Composition rules — how the pieces sit together

Conventions on how the popup actually looks when assembled. These are the team's design defaults — adjust per theme, but start from here.

Vertical stack, top to bottom

  • Header sits at the top — and can stick out beyond the background. The themed logo / mascot in the header is allowed (often expected) to overflow above the background canvas. This is how it gets visual punch.
  • Rewards sits right below the header — often partially overlapping the header from below. Tight stacking, not loose.
  • Quests fill the centre of the background — this is the visual focal point of the whole popup. Make them as visible as possible in the centre. Everything else exists to frame the quests.
  • Description (if used) floats either right under rewards or near the bottom of the background — wherever it doesn't fight the quests for attention. Stay out of the way, stay legible.
  • Timer is flexible — top (under rewards) or bottom (above button). Pick what the layout breathes for.
  • Button is always at the very bottom. No exceptions.

Width & alignment

  • Header and rewards span almost the full width of the background — as wide as possible, but never wider than the background. Edges should breathe by a few pixels.
  • Everything is centre-aligned. Header, rewards, timer, description, button — all on the horizontal centre line. No left-align, no right-align.
  • Quest icons can overlap. Slight or even 100 % overlap is fine if the composition calls for it (some themes have quests stacked / clustered tightly). Numbering still goes quest1…quest5 regardless of layout.

Per-state visual approach (team convention):

  • Header. active = clean themed header. success = same header + a small amount of confetti. fail = the header desaturated to greyscale.
  • Rewards. active and unclaimed are visually identical (same artwork, same prizes shown). claimed is the same plate with the text "Rewards claimed" + confetti — and that confetti should match the confetti used in header / success. fail is the same plate with just the text "Time's up". All four states must be the same physical size.
  • Quests. Two common visual approaches: (1) checkmark style — colour icon with a green tick badge once collected. (2) monochrome → colour — greyscale until collected, full colour when done.

Button and timer are brand-fixed. They come from one of the four brand UIKits (McLuck / Hello Millions / Playfame / Spin Blitz) and are never customised per theme. Copy as-is from the previous theme of the same brand, place, don't touch.

Real layouts — four shipped questlines side by side

The composition rules above are conventions, not a rigid template. Here's how the same set of components has been arranged across four real shipped themes — same components, very different layouts.

Same components, different compositions. Notice that across all four: header is on top (often overflowing the bg), rewards is right under it, quests fill the centre as the focal point, button is at the very bottom. Everything else — overlap density, quest count, description position, timer placement — varies per theme. That's the latitude you have. Stay inside the rules above; play freely within them.

03 — Foundation

03Component Sets — the dashed-rectangle wrappers

Every required piece in the guide must be wrapped in a Component Set — the dashed-purple rectangle Figma draws around a Component with variants. Even the single-state pieces (background, timer) need it.

What is a Component Set?

It's a Figma container that holds one or more variants of a Component, exposed as a single layer with a State=… property. The plugin reads the variants by their State values: State=active, State=success, etc.

How to create one

  1. Select your Component (the purple-diamond layer).
  2. Top-right of the Properties panel, click the small rhombus icon labelled Add Variant. Figma wraps it in a dashed rectangle and adds a second variant.
  3. Rename each variant State=active, State=success, etc.
  4. For single-state components (background, timer), keep just one variant — but leave the dashed Set wrapper.

Repacking the Set

If you change a variant's size, the Set wrapper doesn't auto-resize. Select the Set and hit ⌘ ⌥ ⇧ R — Figma repacks it to the current contents. Without this, the plugin reads stale dimensions and fails validation.

Why every primitive needs a Set

Even background and timer have only one variant — but they still need to live in a Component Set wrapper.

The current For The Win guide has this wrong. Background and timer there are plain Components, not Component Sets. Fix: select each, hit Add Variant once to create the dashed-rectangle Set, then delete the duplicate variant — leaving just State=default.

Why bother? When you copy-paste between project files, only Component Sets keep the parent reference. Plain Components turn into orphaned instances on the receiving side, and the next dizajner has to manually relink every one. Component Sets travel cleanly.

Mockup itself = Component too

Wrap the assembled mockup frame (Questline: ML SuperBowl) as a Component as well. Then drag instances into your Mobile and Desktop preview frames for visual QA. If the design changes, all previews update at once.

Quick visual test: if you see a dashed-purple rectangle around it, you're good. Solid-purple-only border = plain Component, needs to be wrapped.

04 — Workflow choice

04Approach A vs Approach B

Two legitimate ways to assemble a questline file. Both end up at the same plugin pipeline (Validate → Scan → Preview → Export) and ship the same final ZIP. The difference is how you get a working Figma file in the first place. Pick by situation, not by seniority — both senior and junior designers use both.

APPROACH A · Swap inside template

Theme an existing project

Take a finished questline file from the brand UIKit (e.g. Mission to Grill). Duplicate it. Open each Component Set, and inside each variant's Visuals group, swap the artwork for the new theme. Don't touch layer names, Component Set wrappers, or hierarchy.

Use it when: the brand UIKit already has a questline file you can reuse. This is most routine theme work — Super Bowl over Thanksgiving, Mission to Grill repainted as For The Win, etc.

Trade-off: you don't need to understand how the components are wired internally. If something breaks, you ping someone who knows the from-scratch path.

APPROACH B · Build from scratch

Frame-first, then componentise

Lay out the popup as a regular Figma Frame — header, rewards, quests, button, all as plain frames in the canvas. Tune composition, spacing, art, typography. Get sign-off from design lead and stakeholders. Only after sign-off, convert each piece into a Component, wrap into Component Sets, name everything per the plugin's contract, attach state variants, and reference the components from the assembled mockup as instances.

Use it when: the brand needs a brand-new questline structure that doesn't exist yet, or an existing file is too broken to debug. Sometimes faster to rebuild than to fix.

Trade-off: takes longer up front; demands you know the layer-naming contract by heart and how Component Sets need to be wrapped. Pays off because you control the system root-up.

What's the same in both approaches. The contract with the plugin is identical — same layer names, same Visuals rule, same state variants, same export pipeline. The plugin doesn't know or care which path got you here.

How to choose for your current task. Does a usable questline file already exist for this brand and type? → Approach A. Are you launching a brand-new layout, or has an existing file gone unfixable? → Approach B. It's a per-task decision, not a career level.

05Opening the plugin

Open the brand board for the campaign you're working on. Inside, you'll see a list of pages — past campaigns. Don't dump your design into an existing page. Create a fresh one for every new task:

  1. In the Figma file's left page panel, click + to add a new page.
  2. Drag the new page to the top of the page list — newest task always sits on top so the team can find it without hunting.

06 — Plugin · Validate & Scan

06Validate & Scan tab — green-light the file

The first tab of the plugin. Two-step ritual: Validate first (cheap, instant) → fix anything red or yellow → then Scan. Run things in this order; don't try to scan a file that hasn't passed validation yet.

Before you click anything: check the active type tab at the top of the plugin. The plugin opens on the Wheel tab by default — not Questline. If you select your Questline mockup frame and Validate while the plugin is still on Wheel, you'll get a wall of red errors. Nothing is wrong with your design — the plugin is just looking for Wheel components and not finding any.

Order matters: open plugin → click Questline tab → select frame in Figma → Validate. Skip the tab-check and you'll waste minutes diagnosing fake errors.

The order: Validate → fix → Scan

  1. Validate — the cheap check. Walks the frame, verifies every required layer exists with correct naming and states. No rendering. Run this first. If anything red or yellow appears in the panel — fix it before moving on.
  2. If there are errors: open section 21 — Common mistakes for the catalogue of usual culprits (missing Visuals group, wrong layer name, missing state variant, etc.). Fix them in Figma, click Validate again. Loop until 6/6 green.
  3. Scan Selection — the big primary button. Once validation is clean, this extracts positions + bounds for the JSON. Takes 30–90 seconds depending on Render Quality.

What each button on the tab does

  • Validate — cheap layer check, see step 1 above.
  • Scan Selection — the position/bounds extraction, see step 3.
  • Web Preview — opens the standalone Web Preview tool with reveal animations (covered in section 23).
  • Scan & Export (WebP) — one-click shortcut: scans + exports the WebP ZIP in a single action. Use this when you've already validated separately and you're confident the file is clean. Saves you from going Scan tab → Export tab manually. Don't use it before validation passes — you'll get a broken ZIP.

Fix every coloured row — red AND yellow. Red rows are blocking errors (won't export at all). Yellow rows are warnings (export will run but the popup will misbehave at runtime — wrong size, missing state, off-by-one position). Don't ship until both are gone. The Validate panel must be all-green before you trust the result.

Preview tab — graphics mode (default) and wireframe

The Preview tab opens in graphics mode automatically — your popup as it'll actually look. Use the zoom buttons in the top-right of the preview area to inspect detail. Toggle wireframe mode to verify components are positioned correctly without art distracting you.

Click through every Quest state

Quest = Locked / Active / Unclaimed / Completed. Click each pill at the top, eyeball each variant in the preview. Per Michal's rule, locked looks the same as active and unclaimed looks the same as completed — but you still verify all four are present and correct.

Click through Header states too

Header = Active / Success / Fail. The Active state is what you see by default; click Success and Fail to confirm those visuals fire correctly.

Button states (quick check)

Button is brand-fixed and shouldn't normally change between themes — but click through all four states (Default / Disabled / Hover / Active) to confirm the brand-button copy you used has all variants intact.

10Background

The canvas the whole popup is built on. One State=default.

background · State=default

One Component Set, single variant

Per Michal's guide: "The background is the overall background that is visible as a modal." The whole popup theme art (stadium, character, lighting) is composed inside the Visuals group of this single Component.

Inside the background you may put a second "inner" background — a panel where the collectibles will sit. If you do, that inner background must be bounded by a stroke. This is the only nested-bg pattern allowed.

Description lives inside the background — it is NOT a separate component. (See section 15 — Layer naming for the description's own rules.)

"FREE" collectibles live in the background, not as quests. Some campaigns include a few items the player gets for free — they aren't clickable, they don't have states. Those go directly into the background Component (inside Visuals), not into the quest grid. Mostly applies to Stamp Card variants.

Fix from the in-Figma guide. The current background there is a plain Component, not a Component Set. Wrap it: select → Add Variant (rhombus) → delete extra variant → leave just State=default. Now it copy-pastes cleanly between projects.

Don't grow the bg in the mockup. If your art needs taller, edit the source component, not the instance. The plugin compares mockup-bg dimensions to source-bg dimensions and fails on mismatch.

No fixed pixel sizes — popup must fit an average phone. The 366 × 572 of For The Win is a typical canvas, not a hard rule. You can change the background dimensions (and consequently every component sitting inside it) — what matters is the assembled popup looks right inside the Mobile + Desktop preview frames. That's the entire reason those preview frames exist (see section 20 — Web Preview).

Description (lives inside this background)

If the brief calls for descriptive copy under the header (e.g. "Five or six missions, five field goals, one Ultimate Reward"), this is where it goes — as a text or group layer inside the Visuals of background. Not a separate Component.

  • Source. Text comes verbatim from the copywriter, via the brief. Don't rewrite or improvise — copy as written.
  • Length. 2–4 lines maximum. Anything longer doesn't fit and steals attention from the quests.
  • Alignment. Always centred horizontally. Same as everything else in the popup.
  • Font size. 14–18 px is the working range (most often 14, 16, 17). Drop to 13 px only if you have to. 12 px is the absolute minimum and only when nothing else fits — it reads small.
  • Contrast. Must be very contrasty against the background. Use a hard drop-shadow on the text, OR put a darker pill / panel behind it. Whatever it takes for the text to be instantly legible.
  • Placement. Either right under the rewards plate, OR near the bottom of the background — wherever it doesn't fight the quests for attention while still being noticed.
  • When to skip it. Many themes don't have a description at all. If the brief is silent, don't add one.

12Quests — the quest matrix

Five quest icons (quest1…quest5), each its own Component Set with four state variants. Each instance carries a unique questKey property. Per Michal's guide, only active (player can click on the item) and completed (player has collected the item) render at runtime — the other two are required for validation but no longer used.

How many quests? Roughly 4–6, depending on the brief. Five is the common case (this example). Numbering pattern stays the same: quest1, quest2, … with unique questKey per Component Set. Same item across all quests = 1 design (just duplicate the Component Set). Different items = a separate design per quest, drawn fresh inside each Visuals group.

Properties holds the questKey text layer (never rename it). All variants of the same quest share the same questKey value (quest1, quest2, …).

The duplication pattern

  1. Build quest Component Set with all 4 state variants (locked / active / unclaimed / completed).
  2. Set questKey = "quest1" in Properties of every state.
  3. Duplicate the entire Component Set — don't just rename instances. quest1 → quest2 → quest3 → quest4 → quest5.
  4. Update questKey inside each duplicate (quest2, quest3, …) — across all 4 states of that copy.
  5. Swap the art inside Visuals of each.

Locked & unclaimed are required but no longer used at runtime. Plugin still validates all 4 variants per quest. Pragmatic shortcut, straight from Michal's guide: prepare locked the same as active, and prepare unclaimed the same as completed. Same image, different state name. Validation passes, no extra design work.

Quests can overlap — even fully. Slight overlap, large overlap, or 100 % stacking on top of each other is allowed when the composition calls for it (some themes group the quests tightly together). Numbering still goes quest1…questN regardless of layout.

Two visual styles the team uses for state changes: (1) checkmark badge — colour icon with a green tick once collected; (2) monochrome → colour — greyscale until collected, full colour when done. Either works. Pick what fits the theme.

18 — The most important rule

18The Visuals group becomes a raster

Everything inside a Visuals group gets exported as a flat WebP image. Vector? Becomes pixels. Editable text? Becomes pixels. Auto-layout? Frozen. Per the in-Figma guide: "All visuals go into the visuals group. Simplest version: just an image, change the image selection on the fill."

Inside every Component variant — header, rewards, every quest, every reward state — there's a group named Visuals. That's the rendered surface.

What goes where

  • Inside Visuals — theme illustrations, decorative icons, background art. Anything purely decorative.
  • Outside Visuals — live runtime data: timer text, button label. Runtime needs to update these dynamically — they can't be raster.
  • Button & timer never use image fills. They're vector only — color, gradient, stroke, dropshadow.

The clipping contract — Visuals frame size = artwork size, exactly

Three rules that work together. Skip any one of them and the popup ships broken on web:

  1. Clip Content is ON for every Visuals frame and every variant frame. Settings → "Clip content" checkbox. Always.
  2. Visuals frame fits the artwork tightly. No empty padding around your art, no oversized invisible margins. Resize the Visuals frame down to hug the content.
  3. Visuals frame is never smaller than the artwork inside. If your art overflows the frame, on export the plugin crops whatever bleeds outside — and on web that crop becomes the visible bug.

Why all three matter. If Clip Content is OFF, you don't see the bleed in Figma — the canvas shows the overflow as if it's fine. Then the plugin renders to WebP and silently crops the overflow. Result: popup looks intact in Figma but broken on production. Turning Clip Content ON in Figma reveals the same crop visually — so you catch it before export.

Fast self-check. Select the Visuals frame. Press ⌥ ⇧ K to fit-to-content (or just toggle Resize to fit content in the right panel). If anything jumps in size — your frame had loose margins or a hidden overflow. Fix it now, not on web.

21 — Pitfalls

21Mistakes the plugin will catch (and a few it won't)

VALIDATION FAIL

Resizing a quest instance in the mockup

You scaled quest3 in the mockup to make it look bigger. Plugin reads source-component size, not instance size — sizes mismatch, fails.

Edit the source quest3 Component Set instead. The instance updates automatically.
VALIDATION FAIL

Resizing the background in the mockup

Designer dragged bg height in the mockup. Plugin compares mockup-bg dims to source-bg — mismatch.

Resize the source background Component Set. Mockup will follow.
VALIDATION FAIL

background or timer is plain Component, not Component Set

The current For The Win guide has them this way. Plugin handles it but the file copy-pastes badly to the next project — instances become orphaned.

Wrap each: select → Add Variant (rhombus icon) → delete duplicate → keep State=default only.
VALIDATION FAIL

Missing State=locked or unclaimed on a quest

"They're not used at runtime, why bother." Plugin still validates all 4 quest variants exist.

Duplicate State=active art into State=locked; duplicate State=completed art into State=unclaimed. Same image, just renamed.
VALIDATION FAIL

Renamed Visuals or Properties

Designer cleaned up the layer panel and renamed to "Art" or "Layout". Plugin loses the export target.

Both names are hard-coded. Don't rename.
VALIDATION FAIL

Two quests with the same questKey

Duplicated a quest Set but forgot to update questKey inside Properties — both still say quest3.

Open Properties → text layer questKey → set unique value across all 4 states of that quest.
VALIDATION FAIL

Component Set wrapper has wrong size

You changed a variant's content but the dashed-rect Set wrapper still shows old bounds. Plugin reads stale size.

Select the Component Set, hit ⌘ ⌥ ⇧ R to repack.
SILENT BUG

Decimal X / Y positions (Snap to Pixel Grid is off)

Your component sits at x: 132.4 instead of x: 132. Plugin reads decimals and the runtime renders 1px drift on some viewports — popup elements look shifted by a hair.

Figma → enable Snap to Pixel Grid via ⇧ ⌘ ' (Shift + Cmd + apostrophe). Plus a manual eyeball pass before final export — round any stray decimals to integers.
SILENT BUG

File got progressively broken — keep patching, keep failing

You inherited a file that's been "fixed" five times. Every Validate run finds new errors. Time spent debugging exceeds time it'd take to start over.

Cut your losses. Open the most recent shipped theme as a clean template, duplicate, redo the swap from scratch. Often 2× faster than chasing layered breakage. Senior designers do this routinely (Approach B reflex).
SILENT BUG

Live text put inside Visuals

You put the timer digits or button label inside Visuals. They rasterise — runtime can't update them.

Live text always lives outside Visuals, on top.
SILENT BUG

Image fill on button or timer

Brand asset got recoloured with an image fill for the theme. Plugin docs explicitly forbid image fills on those.

Color/gradient/stroke/shadow only. Copy from UIKit unchanged.
SILENT BUG

Skipped Web Preview

You exported and shipped to Operations without testing the ZIP. Now Ops is bouncing it back because reveal animation breaks.

Always click Web Preview after final export. 30 seconds saves 30 minutes.
SILENT BUG

Scan timeout on heavy themes

Final-pass scan at 4× fails halfway. Vague timeout error.

Settings → bump State Change Delay from 1000 to a higher value if needed.
SILENT BUG

Forgot to switch back to FINAL settings

You shipped the 1× test pass to Ops. Popup looks blurry on retina screens.

Always switch to 1000ms / 4× before the final Scan + Export. No exceptions.

26 — Sync

26Sync the section back to your project board

The plugin runs only under figma@patrianna.com, so testing and final ZIP export happen on the test page in that account. Once the ZIP passes Web Preview and the four context frames look right, the entire section needs to flow back to the original project board so both ends stay in sync.

What "the section" means here: the components, the assembled mockup, and the four context frames — everything you've been working on for this campaign. They live together as one block on the Figma page.

The flow

  1. Designer designs and iterates on the project board (B2Spin account).
  2. Switches to figma@patrianna.com to run the plugin → validates → exports ZIP → opens Web Preview → checks the four context mockups.
  3. Test passes. Now copy the entire section back.
  4. Select the whole block on the Patrianna test page (components + mockup + 4 context frames) → copy.
  5. Switch back to the B2Spin account, open the project board, paste over the previous version.

Why this matters

Without this final sync, the project board ends up with the half-finished version while the polished, exportable version sits stranded on the Patrianna test page. Anyone picking up the campaign later — for revision, copy-edit, or a follow-up campaign — needs to find the latest on the project board.

End state: the project board (B2Spin) and the test page (Patrianna) hold identical copies of the section. Both are valid sources of truth; neither is ahead of the other.
